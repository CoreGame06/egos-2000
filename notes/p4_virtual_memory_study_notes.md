# 虚拟内存与硬件页表 (P4 Virtual Memory) 全景深度复习笔记

## 第一部分：理论基础与实现主线 (基于 p4_vm.md)

### 1. 从“软隔离”走向“硬翻译”
在 Project 3 中，我们利用 Software TLB 实现了虚拟内存假象：每次切换进程，都要将内存数据在后台池与前台 `[0x80200000, 0x80400000)` 之间反复拷贝。虽然配合 PMP（物理内存保护）实现了安全隔离，但这种**重度依赖数据拷贝**的方式成为了系统的性能灾难。
为了消除这一瓶颈，RISC-V 提供了原生的 **Sv32 硬件页表转换机制**。在 Sv32 中，进程的代码就安静地躺在各自的物理内存里，系统只需要拨动硬件寄存器，CPU 就能瞬间完成地址的“空间跳跃”（重定向），实现零拷贝的上下文切换。

### 2. Sv32 两级页表体系与 `satp`
Sv32 采用两级树状数据结构来管理地址转换：
- **页表结构**：分为**根页表 (Root Page Table)** 和**叶页表 (Leaf Page Table)**。每个页表正好占用一个标准内存页 (4KB)，里面均匀分布着 1024 个 4 字节的页表项 (PTE)。
- **寻址核心 (`satp`)**：当 CPU 需要翻译内存时，它会首先去找 `satp` 寄存器。操作系统会提前把根页表的物理页号 (PPN) 存放在这里。有了它，CPU 硬件就能自动开启顺藤摸瓜的 Page Walk（页表遍历）之旅。

### 3. 地址翻译微观解析：从 0x803F_EXXX 到 0x804A_DXXX
官方文档用一个精确的例子展示了页表项的计算和拼接过程：
1. **启动翻译 (`satp`)**：申请物理页 `0x805F_1000` 作为根页表，计算其 PPN 为 `0x805F1`。将 `0x800805F1` 写入 `satp`（最高位 1 代表开启分页机制）。
2. **第一级寻址 (Root)**：提取虚拟地址 `0x803F_E000` 的高 10 位 `VPN[1]`，得出十进制 `512`。申请物理页 `0x8051_5000` 作为叶页表。将叶页表的物理地址和权限位 (`0x1F`) 组装成 `0x2014541F`，填入 `root[512]`。
3. **第二级寻址 (Leaf)**：提取中间 10 位 `VPN[0]`，得出十进制 `1022`。最终数据的物理地址是 `0x804A_D000`。将其组装成 `0x2012B41F` 填入 `leaf[1022]`。
*(注：`0x1F` 表示开启 V、R、W、X、U 这五个关键权限位，允许用户态进程进行读、写、执行)。*

### 4. egos-2000 虚拟内存开发主线
按照文档，在代码实现层面，我们需要完成以下几个核心里程碑：
- **搭建恒等映射 (Identity Map)**：将虚拟地址与物理地址 1:1 映射。这是让底层内核能够直接操控物理硬件的基石。
- **构建独立平行空间**：在 `page_table_map` 中，对于用户进程，除了共享工作目录 `SHELL_WORK_DIR` 外，其它内存全由 `elf_load` 动态分配独立的物理页，再写入它们自己的页表中。在 `page_table_switch` 中，通过切换 `satp` 激活各自的独立幻象。
- **强制特权级降级**：必须在 `grass/init.c` 的 `mret` 处，将所有进程（通过 `mstatus.MPP`）降级为 `U-Mode` (用户态)，从而使得页表机制强制生效。
- **安全防线与内存回收**：在异常处理 `excp_entry` 中拦截企图越权的恶意程序（如 `crash1`），将违规进程绞杀并恢复 Shell。最后，在进程销毁 `mmu_free` 时，不仅要释放数据内存，还要将伴生的“根与叶”页表一并清理，并打印开销统计。

## 第二部分：深度探究与硬核解惑 (全周期讨论汇总)

### 1. PMP 与 MMU 的权责交接 (Exception 1 踩坑记)
- **踩坑现象**：刚实现完页表功能并尝试启动时，系统直接崩溃，抛出了 Exception 1 (Instruction Access Fault，指令访问故障)。
- **深度解答**：这源于 P3 到 P4 的安全防线交接失败。PMP 是底层的物理硬件保护。在 P4 中，我们引入了更加灵活强大的 MMU（页表）来接管内存隔离任务。但如果原本的 PMP 规则仍然处于“限制访问”的状态，即使 MMU 页表允许访问，最终也会被 PMP 硬件无情阻拦，引发防线冲突。
- **解决方案**：在 `mmu_init` 中开启页表机制时，必须利用 `csrw pmpaddr0` 和 `pmpcfg0` 将 PMP 对 4GB 地址空间的限制彻底放开。这就好比将治安权从“城管(PMP)”完全移交给了“法院(MMU)”。

### 2. “先建地基后盖楼”：内核自举与恒等映射的必要性
- **疑问**：为什么系统进程必须在最开始强制建立对全部 6MB RAM 以及外设的 1:1 恒等映射，而用户进程不需要？
- **深度解答**：内核（操作系统自身）在开机阶段，必须直接向真实的物理内存写数据，并直接操控硬件外设寄存器（如网卡、串口）。如果不做恒等映射，一旦开启 MMU 的地址翻译开关，内核试图访问串口 `0x10000000` 时，MMU 就会把它当成普通虚拟地址去查表，最后找不到而导致操作系统“当场自尽”。恒等映射是操作系统在虚拟世界中，维持与现实物理世界通信的唯一桥梁！

### 3. 架构级优化探讨：系统进程的页表共享
- **疑问**：我们现在为 `sys_file`、`sys_process` 等系统进程分别调用了 `pagetable_identity_map`，为它们每个人都分配了一套足足覆盖 6MB 的独立根页表，这似乎很浪费内存？
- **深度解答**：你的直觉非常敏锐！在现代真实工业级 OS（如 Linux）中，所有的内核线程完全是共享同一份“内核页表”的（即共享内核地址空间）。未来我们完全可以进行重构，让 PID 0、1、2 共用一个物理根页表，这不仅能节省大量物理页，更能免去系统进程互相切换时刷新 TLB (`sfence.vma`) 的昂贵性能开销。

### 4. 虚拟内存的安全哲学：白名单机制与 MMU 强制拦截
- **疑问**：把分配的物理地址在内核写死就能绝对安全吗？
- **深度解答**：页表的本质是**“不存在即安全”**。新页表默认全 0 (`V=0`)，没有被内核显式映射的区域（如 `0x80000000` 内核区）在用户进程眼里犹如黑洞。哪怕恶意程序自己拼凑出一个指向内核的指针，纯物理的 MMU 硬件电路在查表时看到 `V=0`，会立刻在纳秒级别掐断流水线抛出 Page Fault，恶意软件连执行下一条指令的机会都没有。加上页表本身对用户进程不可见，使得这种隔离固若金汤。

### 5. 加载器的“连环计”：被破坏的恒等映射幻象
- **疑问**：既然系统进程在最开始做了 1:1 的直接映射（虚拟 0x80200000 = 物理 0x80200000），为何它们强行在 M-Mode 跑还会遇到 Exception 2 崩溃？
- **深度解答**：因为加载器 `elf_load` 做了二次“装修”。它读取二进制文件时，会向 OS 申请一块**全新**的空闲物理页（比如 `0x80403000`）来装代码。接着，它强行覆写了虚拟 `0x80200000` 的页表项，让其指向新的 `0x80403000`。
此时恒等映射已被打破。如果脱离了 MMU（跑在 M-Mode 下直接访问物理内存），CPU 去读物理 0x80200000，只能读到全 0 的未初始化数据，即抛出 Exception 2（非法指令）。

### 6. 微内核生死线与特权级剥夺 (Exception 2 的最终修复)
- **案发现场**：在调度器 `proc_yield` 中，一行旧代码因为看到系统进程（`pid < 5`），就自作主张把它强行推入了 M-Mode，导致其跨过 MMU 撞上空物理内存崩溃。
- **微内核华丽转身**：在开启页表的 P4 阶段，必须强制**所有系统进程降级在 U-Mode 下运行**！这正是 egos-2000 “微内核架构”的设计精髓：将庞杂的服务进程塞进受页表严格保护的用户态沙箱，即使某个服务崩溃，也能通过缺页异常优雅地拦截并重启，绝不会牵连底层极简内核 (`earth`) 的生存。

## 第三部分：实战沙盘推演 —— `echo Hello, World!` 的虚拟内存一生

假设用户在 Shell 输入 `echo Hello, World!`（系统分配 **PID = 6**），我们来完整追踪你编写的 C 代码是如何起作用的：

### 幕一：制造私人密码本 (分配与映射)
`elf_load` 准备加载代码到虚拟地址 `0x80200000`，向物理内存申请了空闲页 **`0x80401000`**，调用 `page_table_map(6, 0x80200, 物理页)`：
1. **初始化地基**：你的代码发现这是 PID 6 第一次来，于是申请物理页 **`0x80402000`** 作为它的专属**根页表 (Root)**。
2. **搭建枝叶**：计算一级索引（`vpn1 = 512`），发现槽位是空的，再次申请物理页 **`0x80403000`** 作为**叶页表 (Leaf)**。
3. **写入规则**：将叶页表物理地址连同权限写进根页表 `root[512]`；再算出二级索引（`vpn0 = 512`），把真正的存放代码的物理地址 `0x80401000` 连同 `USER_RWX` 写进叶页表。

### 幕二：切换平行宇宙 (激活硬件 MMU)
调度器 `proc_yield` 决定让 `echo` 运行，调用 `page_table_switch(6)`：
1. **提取钥匙**：拿出 PID 6 的根页表物理地址 **`0x80402000`**。
2. **锁入硬件**：执行 `asm("csrw satp, %0")`，把这个地址塞给 CPU 核心控制塔。
3. **刷新残影**：执行 `earth->mmu_flush_cache()` 清除旧进程留下的 TLB 缓存。
随着 `mret` 切入 U-Mode，MMU 硬件正式接管。CPU 读取虚拟地址 `0x80200000` 时，MMU 瞬间穿梭两级页表，完美拿到了物理地址 `0x80401000` 中的代码指令。

### 幕三：事了拂衣去 (内存全量回收)
`echo` 执行完毕，生命终结，内核调用 `earth->mmu_free(6)`：
1. **地毯式搜索**：代码遍历全局 `page_info_table`，寻找所有带有 `pid = 6` 标签的物理页。
2. **连根拔起**：被搜出来的不仅包含 `echo` 的代码页和栈空间，还包括你在幕一中亲自申请的**根页表**和**叶页表**物理内存。
3. **清零入库**：将它们全部清零，标记为空闲。物理内存恢复如初，这正是我们在终端上看到 `released 11 pages (2 are page tables)` 的由来！一切仿佛从未发生。
